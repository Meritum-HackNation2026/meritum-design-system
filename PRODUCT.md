## Stack

- **Cloud:** during development the demo runs on the team's own server (meritum.gburek.app). The target is the app in GCP `europe-central2` (Warsaw) with models through Vertex AI in an EU region where the chosen model is available. Cloudflare sits in front of it and is outside the EU, as are live search (Vertex AI Search, `global` location), Discord, GitHub, the EUvsDisinfo MCP server (Vercel) and the optional Google and Microsoft sign-in; the data processors register below says what each one receives. We migrate through CI/CD (CI already runs on GCP runners), possibly during the hackathon. `docker compose up` runs everything locally.
- **Models:** from GCP Vertex AI; any model available there, not necessarily Claude, chosen by configuration. The main model is picked by evaluation runs (pydantic-evals) among models in Vertex AI in an EU region, for low price, high tokens per second and good Polish; Bielik and PLLuM are not candidates. Embeddings: gemini-embedding-001 by default; the evaluation compares it with cheaper models such as text-multilingual-embedding-002 on a retrieval golden set, and a cheaper model that scores better replaces it. Optional EU-provider model: Mistral Small 3.1 in `europe-west4` ($0.10 / $0.30 per 1M input / output tokens). Deterministic settings: temperature 0 and a pinned model version. Audio is transcribed by Speech-to-Text v2 with Chirp 3 in the `eu` multi-region (pl-PL GA, $0.016 per minute on the Standard price list; whether `chirp_3` bills as Standard is unconfirmed).
- **Code today:** a skeleton (health endpoint, a DBOS ping workflow) plus the contracts in meritum-core. We build a walking skeleton end to end first (form, API, DBOS workflow, stub LLM, check record, result card), then replace its parts with real ones; the order is in section 3 of the product document.
- **Code:** all repositories and the system go public at the end of development; the public repository has run instructions with one `docker compose up`. Contracts live in the meritum-core repository as the single source of truth; the design system consumes the generated JSON Schema and TypeScript types. Backend and worker pin meritum-core to an exact commit (`rev` in pyproject.toml plus uv.lock), always a commit from core's `main` (core has no `develop`). After a push to core's `main` that changes `src/`, `contracts/` or `pyproject.toml`, the `bump-dependents.yml` workflow opens or updates bump PRs to `develop` in backend and worker on the `chore/bump-core` branch, and a PR in the design system when the contracts changed.
- **API:** Python, FastAPI, FastMCP, Pydantic, Pydantic AI, DBOS (durable workflows). Ruff and Ty in strict mode. Notifications reach the browser over SSE. The MCP server (Streamable HTTP at a public HTTPS address) has two tools, check a claim and `search_sources`, and works as a connector in ChatGPT, claude.ai and other chat apps.
- **Architecture:** vertical slices by core domain with hexagonal architecture inside each; every domain repeats the same subfolders (`models/`, `dtos/`, `ports/`, `adapters/`, …). Channels (web form, extension, Discord, SMS, MCP) are inbound adapters; the LLM, the web search and the corpus store are outbound adapters behind ports, so a model or provider can be swapped without rebuilding the system. TDD. Architecture tests with pytestarch, behaviour specs with behave.
- **Database:** PostgreSQL with pgvector, Polish full-text search (ispell dictionary in our own container image, since managed Cloud SQL cannot load one) and pg_trgm; hybrid retrieval over the corpus. The corpus lives in one shared `corpus` schema, filled by one ingestion and read by both dev and prd; check records, cases and users stay per environment.
- **Files:** a `BlobStore` port in meritum-core with three adapters: a private Cloud Storage bucket in `europe-central2` for the target deployment (only the backend and worker service accounts have access; a lifecycle rule deletes objects after 30 days, the check-record retention), the local filesystem on a volume for development and our own deployments, and any S3-compatible store for self-hosting (Garage, SeaweedFS; Cloud Storage also speaks the S3 API with HMAC keys).
- **Web search:** the basis is our own corpus from RSS feeds and sitemaps of catalogue domains, with the Fact Check API and EUvsDisinfo for discovery. Live search sits behind a `WebSearch` port; the first adapter is a Vertex AI Search website data store (basic website search, `global` location, INCLUDE patterns for catalogue domains, Enterprise edition at $4 per 1 000 queries after 10 000 free a month), provisioned with Terraform in meritum-infra. A result is only a candidate URL: we fetch the page ourselves, respecting robots.txt and Content-Signal, and only then cite it. The fallback behind the same port is our own SearXNG instance limited to catalogue domains with `site:` filters (it relies on other engines' results and terms); Linkup stays an option. We fetch pages with our own HTTP client and text extraction (e.g. trafilatura), because the verbatim citation check needs the exact text; pages rendered by JavaScript go through a local headless crawler (e.g. Crawl4AI), and Firecrawl is an optional hosted alternative. Grounding with Google Search is rejected (its terms forbid caching or analysing results and using their links for crawling), and so is the Custom Search JSON API (closed to new customers, ends 2027-01-01). Live search runs on every check in parallel with corpus retrieval; the search threshold only decides whether we wait for its result. Pages found live wait in quarantine until an injection scan finishes; after the scan they are evidence in the check that fetched them and are recorded in its check record, and they join the shared corpus with the next snapshot. Scheduled RSS and sitemap ingestion runs as DBOS workflows in meritum-worker without any third-party search; Vertex AI Search is used only for live search during a check.
- **Rate limiting:** the slowapi middleware (per IP address, region and channel) and Cloudflare in front of the API against DDoS. slowapi counts in memory per process, so with several instances we recommend a shared counter in PostgreSQL or Redis.
- **Frontend:** React, shadcn/ui, TanStack Router, TanStack Query, Tailwind CSS v4, Biome in strict mode. From shadcnblocks only free blocks, or none: paid blocks may not go into public repositories.
- **Extension:** Chrome MV3; a „Sprawdź” button under posts and a paste box in the popup, both calling the same API as the web form. It runs on the demo mocks (design-system/demo/platforms/) and on the real sites; injected UI renders in Shadow DOM. Optional for the jury.
- **Discord:** a bot on the same API that answers in server channels and in direct messages, with an invite link to add it to any server. A Discord mock page in the meritum-mocks repository calls the same API, so the jury can test the channel without joining a server.

## Users

- **Citizens** who meet a rumour, a post or a forwarded message and want to know quickly whether it holds up. Many have low digital skills: they should not need to learn verification methods or install anything. Their job: paste the text or link, read a short answer in plain Polish, open the sources if they want.
- **Social media readers** who already use the extension and want to check a post where they see it, with one click.
- **People who prefer Discord or SMS**, who send the text to a bot (in a server channel or a direct message) or to a number and get a short answer with a link to the full result (SMS if time allows).
- **Moderators and analysts** named by the administrator; analysts and admins also run and compare evaluation runs on an evaluation page in the web app, who signs them in to the moderator panel with a role (moderator, analyst, admin) and keeps the list of high-risk topics. Their job: take over unanswered claims (a claim whose verdict is „insufficient evidence”) that are high-risk or repeated, and claims a user disputed with „Zgłoś błąd”, see similar claims grouped into one case, and track quality: abstentions, injection attempts, response time, cost.
- **Jury** of the MSZ „Prawdowid” challenge, who run the reference set themselves, without the team's help, through the web form and the Discord mock; the extension is optional.

## Product Purpose

A tool that lets a citizen check a claim as easily as sending a message, grounded in an audited set of credible sources. The system extracts the claims worth checking, searches official documents, public data and fact-checkers' corpora (plus fresh publications from catalogue domains), and gives each claim one of five verdicts: confirmed, false, misleading, insufficient evidence, not verifiable. Every finding cites the source (title, publisher, date, link, verbatim fragment); the strength of the answer follows from explicit premises; when evidence is missing the system says so and explains what it could not establish. Technical failure, a request for clarification and out-of-scope input are never shown as verdicts. Instructions found in checked content never change how the system behaves.

Success: a citizen gets an honest, sourced answer through the channel they already use, and we optimise towards 30 seconds at most per check (the brief asks for a median of 30 s or less; nothing special happens after 30 s); the jury gets the same substantive result through the web form and Discord; nobody is shown a model's guess dressed up as a fact.

The product is entered in one hackathon challenge: **MSZ „Prawdowid”** (fast, easy verification based on credible sources). The full brief is in `../konkursy/`.

## Positioning

Honest by construction: the language model reads, searches and writes, but a verdict needs a verbatim citation, its strength is computed from premises by a fixed rule, and abstaining is a first-class answer. Meets people where they already are (a web page anyone can open, a Discord bot, and a button under the post they are looking at). Auditable: open source catalogue with reasons for inclusion and exclusion, a record of every check, public code at the end of development, and a register of data processors that says what is processed in the EU and what is not.

## Operating Context

- Primary channel: a responsive web form. Conversation history stays in the browser's sessionStorage. Signing in with a Google or Microsoft account is optional and never required; signed-in users keep their conversations on the server, can return to them from another device and can delete them. Every channel says at first contact that an AI system answers (AI Act art. 50, applicable from 2026-08-02). Notifications (progress, finished checks, moderator answers, new evidence, system news) arrive as Sonner toasts over SSE or WebSocket from DBOS events; a toast not acted on stays in the inbox as unread. Second channel: the Discord bot on the same API, built from the start; it accepts text, links and voice messages, and splits its answer into a summary message with a link to the full card plus one message per claim, each within Discord's 2 000-character message limit and never cutting a citation; together with the web form it meets the two-channel requirement whatever the mentors decide about the extension. The Chrome extension (button under posts plus the popup paste box) is an extra channel on the same core. If time allows, an SMS demo adapter: an SMS gateway webhook on the same API, operator fees stated plainly. Polish text forces UCS-2 (70 characters), so the SMS answer carries the main claim's verdict and a link to the full result; transliteration to GSM-7 (160 characters) is an option. Consistency: results are cached by normalised input for a fixed time (for example 2 hours) regardless of new corpus snapshots, so the same input gives the same substantive result in every channel while the entry lives. The cache keeps only the substantive part (claims, limitations, corpus version, cited source ids); escalation and the repeat counter are computed on every request, and technical failures are never cached.
- The extension injects UI into third-party feeds in light and dark themes. Per-platform skins (X, Facebook, Instagram, Reddit, TikTok) adapt font, radius, surface, borders and links; the Meritum mark, the verdict word and colour, and the sources block never change. It sends content only after the user clicks.
- Demo for the jury: the same question asked in the web form and on the Discord mock (or the real bot via its invite link), a sourced verdict, an honest abstention with a moderator case, an ignored prompt-injection attempt, and the evaluation results on our own published test set (the brief's „open set”; the jury's reference set from MSZ is hidden). The extension on an X mock is an optional extra; nobody has to enable developer mode. Film under 3 minutes, deck under 12 slides.
- The jury runs it from our instructions, end to end, with no manual help. Nothing in the answer may depend on hard-coded examples.

## Capabilities and Constraints

- Input: text, an http(s) URL or an audio file / Discord voice message (MVP); image with OCR, metadata and reverse search (if time allows). Until OCR exists, an image gets the out-of-scope status with a message, and README lists it among unsupported cases. Out of scope is only for an unsupported input type or a request that is not about information; „needs clarification” only when no claim can be extracted; every factual claim gets a verdict, so scenario D ends with „insufficient evidence”. An unreachable or paywalled URL is a technical failure. Input validation, length limit, rate limit, automatic masking of obvious personal data.
- Claim extraction: one or more claims per input, facts separated from opinions.
- Retrieval: corpus built from the source catalogue, scraped, chunked and vectorised: at least 100 documents from at least 10 domains and two source types. Primary sources: the organiser's list (official gov.pl and agency sites, including gov.pl/web/dyplomacja) plus ISAP and EUR-Lex for legal acts, dane.gov.pl for public data and the BIP pages of catalogue institutions, which §7 of the brief recommends; each entry states why it qualifies. Secondary sources: articles from fakenews.pl and pravda.org.pl (IFCN signatories, no robots blocks, RSS and sitemaps) and EUvsDisinfo `fact` texts (publisher id `eeas-euvsdisinfo`). Demagog and AFP Sprawdzam block bots, so we only take their ClaimReview rating and link from the Google Fact Check Tools API, never stored beyond its cache headers. A rating from an IFCN or EFCSN fact-checker can be a premise for a settling verdict: the citation is the fact-checker's name, the rating exactly as published, the title, date and link, with no fragment of their page, and it counts as one secondary publisher ("Według Demagoga …"); Konkret24 is excluded (not in IFCN or EFCSN, and TVN requires a licence agreement). robots.txt, Content-Signal and TDM reservations are checked per domain. Full text is kept 90 days from `fetched_at` (renewed on refetch); metadata and cited fragments live as long as the check record that cites them. Each document has publication and retrieval timestamps and each catalogue entry a publisher id. Live web search runs only on catalogue domains, on every check. The organisers consented to processing the listed sources; we have no written source for that yet, and it does not cover third-party rights, so in production every consent gets confirmed legally with each provider. The organiser's incident database and EUvsDisinfo are one MVP feature: a DBOS workflow keeps a local EUvsDisinfo copy through its MCP server (pages of 100, full rescans stored as deltas) as described in https://euvsdisinfo.eu/public-docs/How_to_grab_all_Articles_and_Cases_from_disinfo.pdf; the token is issued on e-mail request and we found no licence for the database. Matches are context, `fact` texts are citations, and disinformation links are shown to moderators only.
- Verdict per claim with citations, premises and strength. Only settling verdicts (confirmed, false, misleading) have a strength, and it counts only publishers (by catalogue publisher id) whose citations agree with the verdict: strong needs 2 or more agreeing independent publishers, at least one of them primary, and fresh evidence; moderate needs 2 agreeing publishers or 1 primary; one non-primary publisher or outdated evidence gives weak. Agreement follows from citation stances. Conflicting credible sources give „insufficient evidence” with both sides cited side by side, a plain note on what differs and no strength. Each claim has a date it refers to and where that date came from (the text, the input's publication date, or today); evidence age is measured against it (365 days by default, hours or days for short-lived sources set per catalogue entry), and the card shows both dates. Legal acts in force, official pages updated in place and evidence about a past event never count as outdated; validity is set per citation. Evidence that newer evidence superseded by the claim date (validity `superseded`, set by a deterministic rule) is shown on the timeline but neither conflicts nor counts towards strength. Outdated evidence („dowód nieaktualny”) is distinct from old content resurfacing as new (scenario B), which is „misleading” with an outdated or out-of-context technique. A neutral source-status warning only for entities on the official EU sanctions list; a match to known incidents as context only, and a domain from the incident database triggers a warning only when the checked link is on that domain and the incident's topic matches the claim. Neither ever changes the verdict.
- Abstention without a fake answer, with what is missing. A moderator case opens automatically for an unanswered claim on a high-risk topic (embedding similarity above a threshold against the admin's topic list, with a keyword list as fallback; no model classification), for the second similar unanswered claim from anyone in any channel, or when a user presses „Zgłoś błąd”. The number of distinct askers only raises priority; rate limits handle spam. Similarity is measured per claim, a case holds its claims and their checks, and it can have several reasons at once. The UI distinguishes „recommended for hand-off” from „handed off”, and joining an existing case never reveals that someone else asked.
- Prompt-injection resistance: user input, a user-supplied URL and source text are marked as data in every step; our own detector (Polish and English patterns plus an isolated LLM classifier) sits in front of every model call; a dedicated injection classifier, Model Armor or Prompt Guard / Llama Guard on Cloudflare Workers AI, is picked on our golden set (Model Armor: Polish is not among its tested languages, multilingual detection with residency only in the `eu` multi-region). Retrieved fragments are reranked by a cross-encoder (Vertex AI ranking API or bge-reranker) before the model, and personal data is masked by Google Sensitive Data Protection in the EU; resistance is measured on a Polish attack set; catalogue pages are scanned at ingestion and live-search pages stay in quarantine until scanned. An instruction in user content is cut out and the rest is analysed as data; a source containing one drops out of the evidence; every attempt is logged. An attempt counts as repelled when the verdict matches the label of the same case without the instruction, the event is logged and no instruction was executed.
- Failures: when a web search we wait for fails, times out or hits a limit, or the model fails after retries, the user gets a technical-failure message, never an answer.
- Speed: several research agents (corpus, live search, fact-checkers) run in parallel and the main agent streams draft answers with research progress; a draft shows no verdict until citations pass verification. Latency comes from the check record (received to answered, through the channel); in the evaluation harness a failed case returns a status instead of raising, so it stays in the median.
- Cost and scale: cost per check from token usage and search calls in the check record, cost of 1 000 queries and of keeping each channel, result-cache hit rate, a DBOS queue with a concurrency limit, HTTP 429 with a clear message under heavy traffic, autoscaling on GCP. DBOS has no „full queue”, so the 429 comes from our own counter of waiting checks. Numbers come from measurement during implementation. Accepted risks: per-citation stance calls multiply model and screening calls, and slowapi counts per process; recommended but not committed: caching scan results by fragment hash, one stance call per claim with isolated pairs, a shared counter in PostgreSQL or Redis.
- Check record: question (masked), time, channel, sources (including live-search pages), verdicts, models used, processing region, cost, latency, cache hit, retrieval errors, injection events; defined retention and a „delete my checks” action for the session; signed-in users also have a user id and can delete their history and account. Masking also covers DBOS step outputs (fetched pages, model outputs), and retention and deletion cover the DBOS system tables. IP address handling and log retention are set in the privacy policy. Channels other than the browser have their own privacy policies: Discord gives a username and user id and SMS a phone number, which we process only to reply and count repeats, store as a salted hash with the same 30-day retention and never show to moderators; „/usun-moje-dane” on Discord and the SMS keyword „USUN” delete the records for that identifier. Usage telemetry is aggregate only, and IP and region are used only against attacks.
- Evaluation with pydantic-evals on our golden set (zestaw deweloperski), built from the same materials as the knowledge base and covering the brief's scenarios A–J. We publish it and ask the mentors whether MSZ will publish a public part of its reference set; if so, we report on both. Thresholds are tuned only on the golden set. Evaluation mode pins `corpus_version` and replays recorded provider responses; we publish case files, URLs, fragments and a snapshot manifest (ids, checksums, `fetched_at`), never full texts. Evaluation never runs in CI, not even a subset: runs start manually or on a schedule, outside the PR checks; analysts start, upload and compare runs on an evaluation page, and runs execute asynchronously in the worker. A case's verdict is the verdict of the main claim named in the case file (with several labelled claims, the worst result by a fixed order); non-verdict statuses are their own error class in macro-F1. The script reports macro-F1, citation coverage and correctness, abstention, injection resistance, median latency and cost per 100 checks.
- Exports (if time allows): JSON, CSV and a STIX 2.1 bundle for OpenCTI; technique codes mapped to DISARM, marked „to be confirmed by an analyst”.
- Jury without keys: README gives two paths, the public demo and a local run with own keys; missing keys are reported at startup by the readiness check, never inside answers.
- Controlled archiving of user-indicated material (if time allows) only with a recorded legal basis, retention, access control and deletion procedure.
- UI language: Polish, plain words. Working name: **Meritum**, subtitle „obywatelski radar dezinformacji”.

## Product Principles

1. No source, no finding: every claim the system presents as established leads to a verbatim fragment of a named source.
2. Abstaining is an answer: when evidence is missing or conflicting, say so plainly and say what is missing.
3. Model interpretation is labelled as such and kept apart from source material.
4. Strength comes from premises the reader can see: number of independent sources, official or primary sources, recency, agreement.
5. Never judge by who said it: domain, author, channel, popularity or source status alone never decide a verdict.
6. Failure is not a verdict: outages, missing keys, limits and failed web searches or model calls are reported as technical problems.
7. Support, not a judge of truth: the answer invites the reader to open the evidence; people handle what the system cannot settle.
